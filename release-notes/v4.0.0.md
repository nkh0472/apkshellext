# ApkShellext2 4.0.0

The shell layer is now part of this repository: the four handlers and the context menu no
longer run on a vendored third-party shell framework copy, and Windows 11 22H2 and later get
the modern `IExplorerCommand` menu. The dll drops by 256,000 B (−22.0%), the 87-sample icon
corpus is still byte-identical, and the package verifies the registration it just wrote.

## Highlights

- **The shell layer is in-repo.** `ApkShellext2\Shell` implements the icon, info-tip and
  thumbnail handlers plus the context menu against the Windows shell interfaces directly;
  `ApkShellext2\Registration` writes the same registry shape `regasm /codebase` writes. The
  vendored shell-framework source tree is deleted, so nothing outside this repository supplies
  the COM classes any more and the dll shrinks from 1,165,312 B to 909,312 B.
- **Modern context menu.** On Windows 11 22H2 (build 22621) and later, `IExplorerCommand`
  provides the modern menu; Windows 10 and the Windows 11 "Show more options" entry keep the
  classic `IContextMenu` menu. Both render the same command model, so the items and their
  order are identical.
- **Export info (CSV)…** is a new context command: it writes one UTF-8 (BOM) row per selected
  package with file and folder, app name, package name, version and revision, publisher, app
  id, type, size, modified time and a status column - a selection that contains an unreadable
  file still produces a row for it.
- **Preferences inserts rename variables by click.** The rename pattern field now lists the
  available variables next to it; clicking one inserts it at the caret.
- **`update.bat` finishes its job.** After registering, it reads every handler slot back from
  the file class of all eight extensions (46 slots for a per-user install: two class roots) and
  compares the default values with this package's class ids; a mismatch prints the registry
  path and exits 1. A migration update also moves the installed `update.bat` into the backup
  folder, so `/rollback` restores exactly the previous file set — and an install that never
  shipped the updater does not gain one from a rollback.

| 7z package (`ApkShellext2-3.6.0.7z` / `ApkShellext2-4.0.0.7z`) | 746,997 B | 698,946 B | −48,051 B (−6.4%) |
| Deployment tree | 2,344,225 B / 27 files | 2,123,962 B / 28 files | −220,263 B (−9.4%) |

The deployment tree grew by one root file because the package now ships `update.bat`: nine
root files (the dll, six `.bat` scripts and the two libwebp dlls) plus the 19 satellite
resource assemblies. The 7z size moves by a few hundred bytes between runs because archive
timestamps are not normalized. Numbers were measured with a Visual Studio Release build; the
dotnet-CLI route produces the same dll size.

## Breaking-ish changes

- **The COM class names changed.** The four class ids are the same as in 3.6.0, but
  `InprocServer32` no longer names `ApkShellext2.ApkIconHandler` and friends: it names
  `ApkShellext2.Shell.Native.IconHandlerNative`, `InfoTipHandlerNative`,
  `ThumbnailHandlerNative` and `ContextMenuHandler` (plus the `IExplorerCommand` class). A
  registration written by 3.6.0 keeps working only until the new package is installed — use
  `update.bat` (or reinstall) rather than copying the dll over an old registration.
- **`update.bat` now fails loudly.** A handler slot that does not hold this package's class id
  makes the update exit 1 instead of printing a warning and returning 0. Scripts that ignored
  the exit code now see the failure; a warning-only result is no longer available.
- **The package has nine root files** (it gains `update.bat`). Tools that expect the 3.6.0
  eight-file layout need the new manifest.
- **`/rollback` may delete `update.bat`.** Rolling back an in-place update in an install that
  never shipped the updater removes it, so the folder returns to its previous file set.
- The classic menu runs on the same Windows versions as 3.6.0; the modern menu requires
  Windows 11 22H2 (build 22621) or later, and one package serves both.

## Known issues

- **The modern menu is not verified on Windows 11.** Development and testing happen on
  Windows 10, so the `IExplorerCommand` path has unit coverage but no on-screen verification.
  Before a public 4.0.0 release someone has to confirm on a Windows 11 machine: the title and
  icon of the top-level item, the subcommand order and enabled state, multi-select with
  `MultiSelectModel=Player`, and that "Show more options" still shows the classic menu.
- **Subcommands of subcommands do not expand.** The shell SDK does not allow an
  `IExplorerCommand` item to carry subcommands of its own, so the two nested menus
  **Dump** and **Search in Stores** may not open. The classic menu is unaffected.
- **A deflated inner `.appx` in an `.appxbundle` still fails** with
  `NotSupportedException: zip containers must be opened from a seekable stream`; stored inner
  packages read fine (unchanged since 3.6.0).
- **Windows 11 does not call the `.appx`/`.appxbundle` icon handler**; those files show the
  system package icon. The context menu and the info tip still work.
- **Machine-wide (`HKLM`) installation is not verified without administrator rights.** The
  per-user path is the tested one; `install.bat` is unchanged from 3.6.0 apart from what it
  registers.
- **Stale icon and thumbnail caches hide the new handlers.** An icon or thumbnail Explorer
  failed to produce before the upgrade stays cached as that failure; delete `thumbcache_*.db`
  and `iconcache_*.db` under `%LOCALAPPDATA%\Microsoft\Windows\Explorer` with Explorer stopped,
  then restart Explorer.

## Upgrade notes

- Extract the new package anywhere and run `update.bat` from it: it finds the registered
  install folder through the COM `CodeBase` value, moves the files this version replaces (and
  the ones 3.6.0 no longer ships) into `backup-<oldversion>-<timestamp>`, copies the new files
  in, re-registers the same scope and verifies the slots. `update.bat /rollback` restores the
  newest backup.
- Per-user and machine-wide installs upgrade the same way; the scope is read from the
  registration, so an install made by `install_user.bat` is not turned into an `HKLM` one.
- A fresh install is unchanged: `install.bat` (elevated) or `install_user.bat` (per-user),
  then `restart_explorer.bat` if the icons do not refresh.
- Settings live under `HKCU\SOFTWARE\ApkShellext2` and are not touched by the upgrade. The
  registry value name `SharpShell_Backup_DefaultIcon` is kept as-is: it is the marker that
  stores the `DefaultIcon` value from before the extension took the file type over, so
  renaming it would lose that backup for existing installs.
- The four class ids themselves are unchanged, so nothing that references a class id has to
  be re-created.
